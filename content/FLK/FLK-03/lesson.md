# FLK-03 · Time & windows — watermarks, idleness, lateness, late side outputs

## Why event time exists

In a batch mart you decide the grain ("daily GMV per company") and the data is already complete when
you compute it. Streaming breaks that comfort: events arrive **out of order** and **late**. A sale
that happened at 09:59 can show up at 10:03 — after you've "closed" the 09:00–10:00 hour. If you
bucket by **arrival time** (processing time), that sale lands in the wrong hour and your hourly GMV
is wrong whenever the network hiccups. The number is no longer reproducible: replay the same events
and you get a different answer because timing changed.

Flink's answer is **event time**: bucket by *when the event happened* (a timestamp in the data), not
when Flink saw it. Then two questions remain:

1. **When is an hour "done" enough to emit a result?** → **watermarks.**
2. **What about events that arrive after that?** → **allowed lateness + late side outputs.**

This is exactly the "late-arriving fact" problem you already know from SCD2 and event marts, made
first-class.

## How watermarks work

A **watermark** is a marker that flows with the stream saying *"I believe no event with a timestamp
≤ T will arrive after this."* When a watermark of T passes an event-time window whose end is ≤ T,
the window **fires** (emits its result). Watermarks are generated by a **`WatermarkStrategy`**:

```java
WatermarkStrategy
    .<Order>forBoundedOutOfOrderness(Duration.ofSeconds(5))   // tolerate 5s of out-of-order
    .withTimestampAssigner((o, ts) -> o.eventTimeMs);
```

`forBoundedOutOfOrderness(d)` emits a watermark of `(max event timestamp seen) − d`. A larger `d`
tolerates more out-of-order data but delays results; a smaller `d` is prompt but drops more as late.
`forMonotonousTimestamps()` is the `d = 0` special case for already-ordered streams.

### Windows

A window assigner slices the keyed stream into finite buckets:

| Assigner | Shape | Use |
|---|---|---|
| **Tumbling** | fixed, non-overlapping (hourly GMV) | periodic aggregates on a fixed grain |
| **Sliding** | fixed size, steps smaller than size (overlap) | moving averages / rolling windows |
| **Session** | gap-based: a window closes after a gap of inactivity | user sessions, bursts |

In Flink 2.x you build them with `java.time.Duration` (the old `Time` class is gone):
`window(TumblingEventTimeWindows.of(Duration.ofHours(1)))`.

### Firing, lateness, and the late side output

The default is: a window fires once when the watermark passes its end, then its state is purged.
Two knobs change that:

- **`allowedLateness(d)`** keeps the window state for an extra `d` after firing. Events that arrive
  late but within `d` **re-fire** the window (an updated result). After `end + d`, the state is
  dropped.
- **`sideOutputLateData(tag)`** routes events that arrive **after** the window can still accept them
  (past `end + allowedLateness`) to a side-output stream instead of silently dropping them. This is
  your dead-letter for late facts — you can audit or reconcile them.

Without a late side output, Flink **silently drops** events that arrive after the watermark has
passed their window. That silent drop is the classic streaming bug: your totals are quietly short
and nothing tells you.

## Idleness: the stuck-watermark trap

A keyed/partitioned source has **per-partition** watermarks, and the operator's watermark is the
**minimum** across its input partitions (you can't declare time has advanced past data a slow
partition might still produce). That minimum rule has a sharp edge: if **one partition goes quiet**
(no events, e.g. a region with no overnight traffic), its watermark **stops advancing**, so the
*combined* watermark freezes at that partition's last value — and **every window stops firing**,
even for busy partitions. Results just stop coming.

The fix is **idleness**:

```java
WatermarkStrategy.<Order>forBoundedOutOfOrderness(Duration.ofSeconds(5))
    .withTimestampAssigner(...)
    .withIdleness(Duration.ofSeconds(10));   // mark a quiet partition idle after 10s
```

`withIdleness(d)` marks a partition **idle** if it produces no events for `d`. An idle partition is
**excluded** from the watermark minimum, so the combined watermark can advance on the active
partitions alone and windows fire again. When the partition produces data again it becomes active
and rejoins the minimum. Forgetting idleness on a stream that can have quiet partitions is a
production outage waiting to happen: the job runs fine in testing (all partitions busy) and stalls
in production the first quiet night.

## From your world

| SCD2 / event mart | Flink time & windows |
|---|---|
| Late-arriving fact needing a back-dated correction | event-time window + allowed lateness (re-fire) |
| "As-of" grain | the event-time window boundary, not arrival time |
| A reconciliation/exception table for late loads | the **late side output** stream |
| A silently short daily total after a load delay | the bug you avoid by using event time + a late side output |
| A region with no overnight sales stalling a global rollup | the idleness fix |

## When NOT to reach for complex windowing

- **Already-ordered, complete input.** If your source guarantees in-order, on-time events (rare), a
  simple `forMonotonousTimestamps()` and plain tumbling windows are enough — no lateness machinery.
- **Processing-time is genuinely fine.** For "events in the last 5 minutes of wall-clock, best
  effort" (e.g. a liveness dashboard), processing-time windows are simpler and you don't care about
  reproducibility.
- **Pure batch reprocessing.** Bounded, complete data computed with SQL/dbt doesn't need watermarks.
